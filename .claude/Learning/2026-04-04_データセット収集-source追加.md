# データセット収集設計・source.jpg 追加・EXIF メタデータ保存

**日付**: 2026-04-04
**会話の概要**: AIに自分の色味の好みを学習させるためのデータ収集フローを整理し、生写真（source.jpg）の保存追加と、撮影時のEXIF情報（ISO・露出時間など）を recipe.json に含める実装を行った。

---

## 今日学んだ概念

### AI学習のための「入出力ペア」

- **何か**: AIに何かを学ばせるには「入力」と「正解の出力」のセットをたくさん集める必要がある
- **なぜ必要か**: AIは「この入力が来たらこの出力を返すべき」というパターンを大量の例から学ぶ。片方しかないと学べない
- **例え**: 料理の味付けを学ぶシェフに「完成した料理の写真」だけ見せても何も学べない。「食材の状態（before）」と「完成品（after）」と「使ったレシピ」の3点セットがあって初めて「この食材にはこの味付けが合う」と学べる

FlashFilmの場合：

| 役割 | ファイル | 意味 |
|------|---------|------|
| AIへの入力 | `source.jpg` | 撮影した生写真（加工前） |
| 参考出力 | `target.jpg` | 手動で色味を整えた加工済み画像 |
| 正解ラベル | `recipe.json` | どのパラメータをどう動かしたか（数値） |

→ AIは「この生写真（source）→このレシピ（recipe）」の対応を学ぶ

---

### フェーズ分けの考え方（MLプロジェクトの典型構造）

- **何か**: 機械学習プロジェクトは「データ収集 → 学習 → 推論」の3フェーズに分かれる
- **なぜ必要か**: 一気に全部作ろうとすると複雑になりすぎる。フェーズごとに独立して進められる
- **今どこか**: FlashFilmは現在フェーズ1（データ収集）の実装中

```
フェーズ1: データ収集（← 今ここ）
  写真撮影 → 手動編集 → Save → source.jpg + target.jpg + recipe.json が溜まる

フェーズ2: AI学習（オフライン・アプリ外の作業）
  溜まったペアでモデルを訓練する

フェーズ3: AI推論（feature/ai-integration で実装予定）
  新しい写真 → モデルがレシピを予測 → スライダーに自動反映
```

---

### ローカル開発サーバーとの通信

- **何か**: `__DEV__` モード（開発中）では、アプリがデータをローカルのサーバーに送信して保存する仕組み
- **なぜ必要か**: スマホアプリはファイルシステムへの直接アクセスが制限されている。開発中はPCのフォルダに直接データを溜めたいため、ローカルサーバー経由で保存する
- **エラーとの関係**: `Network request failed` が出る場合は `npm run step4:collector` が起動していない。アプリを使う前に必ずこのコマンドをターミナルで実行する必要がある

```
アプリ（iOS Simulator）
    ↓ POST /api/step4/save  ← これが失敗すると Network request failed
サーバー（127.0.0.1:43110）
    ↓ writeFile
dataset/step4/sample-XXXX/
```

type SaveDatasetSampleInput = {

  recipePath: string;

**ポイント解説:**
- `sourceUri`: アプリ内での画像ファイルの場所を表す文字列。`file://` から始まるパスが渡される
- 型に追加するだけでなく、実際に使う関数にも渡さないと意味がない（次のコードで）

### `saveToAppSandbox` — 本番環境での source.jpg 保存

```typescript
const saveToAppSandbox = async ({
  sourceUri,  // ← 追加
  targetUri,
  recipe,
  sampleId,
}: SaveDatasetSampleInput): Promise<SaveDatasetSampleResult> => {
  // ...
  const sourcePath = `${sampleDir}source.jpg`;  // ← 追加
  const targetPath = `${sampleDir}target.jpg`;
  const recipePath = `${sampleDir}recipe.json`;

  await FileSystem.copyAsync({           // ← 追加
    from: normalizeUri(sourceUri),
    to: sourcePath,
  });
  await FileSystem.copyAsync({
    from: normalizeUri(targetUri),
    to: targetPath,
  });
  // ...
  return {
    sampleId: resolvedSampleId,
    sourcePath,  // ← 追加
    targetPath,
    recipePath,
  };
};
```

**ポイント解説:**
- `FileSystem.copyAsync`: expo-file-system のメソッド。`from` のファイルを `to` にコピーする
- `normalizeUri`: URI の形式を統一するユーティリティ（`/path/...` → `file:///path/...` に変換）

### `saveToCollector` — 開発サーバーへの sourceBase64 送信

```typescript
// saveToCollector の body に sourceBase64 を追加
body: JSON.stringify({
  sampleId,
  sourceBase64,  // ← 追加
  targetBase64,
  recipe,
}),
```

**ポイント解説:**
- `Base64`: バイナリデータ（画像）をテキスト（文字列）に変換したもの。JSONに画像を含めるために使う
- サーバー側でこの文字列を受け取り、`Buffer.from(sourceBase64, 'base64')` で元のバイナリに戻して保存する

### `step4-collector-server.mjs` — サーバー側での source.jpg 保存

```javascript
const { sampleId, sourceBase64, targetBase64, recipe } = payload;  // ← sourceBase64 追加

// バリデーション（sourceBase64 の存在チェックも追加）
if (
  !isNonEmptyString(sampleId) ||
  !isNonEmptyString(sourceBase64) ||  // ← 追加
  !isNonEmptyString(targetBase64) ||
  recipe == null || typeof recipe !== 'object'
) { ... }

const sourcePath = path.join(sampleDir, 'source.jpg');  // ← 追加

await writeFile(sourcePath, Buffer.from(sourceBase64, 'base64'));  // ← 追加
await writeFile(targetPath, Buffer.from(targetBase64, 'base64'));
```

**ポイント解説:**
- `Buffer.from(base64String, 'base64')`: Base64文字列をバイナリデータに変換。Node.js（サーバー側）での書き方
- アプリ側とサーバー側の両方を変更しないと、片方だけではデータが不整合になる

### `ImageProcessingScreen.tsx` — photo.uri を sourceUri として渡す

```typescript
// 調整あり：加工済み画像を tempPath に書き出してから保存
saved = await saveDatasetSample({
  sourceUri: photo.uri,   // ← 追加（生写真のURI）
  targetUri: tempPath,    // 加工済み画像の一時ファイルパス
  recipe,
});

// 調整なし：元画像をそのまま target としても保存
saved = await saveDatasetSample({
  sourceUri: photo.uri,   // ← 追加
  targetUri: photo.uri,   // target も元画像と同じ
  recipe,
});
```

**ポイント解説:**
- `photo.uri`: カメラ画面から渡された生写真のURI。`route.params.photo.uri` で取得している
- 「調整なし」の場合は source と target が同じファイルになるが、それは正しい（変更がなければ加工前 = 加工後）

---

## なぜそう書くか（設計の理由）

- **source と target を両方保存する**: AIの学習には「変換前（source）→ レシピ（recipe）」の対応が必要。target.jpg は「ビジュアルで確認するための参考」として残す設計。将来的にモデルが target の見た目を評価指標にも使える

- **調整なしの場合も sourceUri を渡す**: `saveDatasetSample` の型に `sourceUri` が必須になったため、調整なしのパスでも渡す必要がある。このとき `sourceUri === targetUri` になるが、「調整なし＝生写真のまま保存」という事実を正確に表している

- **サーバー側のバリデーションにも追加する**: `sourceBase64` の存在チェックをサーバー側にも追加した。クライアント側でバグがあって空文字を送った場合に、中途半端なデータ（source.jpg なし）がディスクに保存されるのを防ぐため

## EXIFメタデータの追加（後半）

### EXIFとは

- **何か**: カメラが撮影時に画像ファイルに自動で書き込む撮影情報
- **なぜ必要か**: AIが「この写真はISO高い（暗い環境）→ brightnessを上げるべき」といった判断の補助情報として使える
- **注意**: 深層学習モデルならピクセルから直接学べるため効果は限定的。「分析・デバッグ用に残しておく」という目的のほうが現実的

取得できる主なEXIF値：

| キー | 内容 | 例 |
|------|------|----|
| `ISOSpeedRatings` | ISO感度（数値が高いほど暗い環境） | `800` |
| `ExposureTime` | シャッタースピード（秒） | `0.016` |
| `WhiteBalance` | ホワイトバランス（0=auto, 1=manual） | `0` |
| `Flash` | フラッシュ発光フラグ（ビット0が1なら発光） | `1` |

---

### `metadata: null` になる理由（dev デフォルト画像の場合）

- **何か**: 開発中は `takePictureAsync` を使わず静的アセット画像を使うため、EXIFが存在しない
- **なぜ問題ないか**: 本番で実機撮影すれば値が入る。`metadata: null` のサンプルは学習時に除外するか「情報なし」として扱えばよい

```
実機カメラ撮影 → exif あり → metadata: { iso: 800, ... }
dev デフォルト画像 → exif なし → metadata: null  ← これは正常
```

## 書いたコード（EXIFメタデータ追加分）

### `camera.ts` — CapturedPhoto に exif フィールド追加

```typescript
export type CapturedPhoto = {
  width: number;
  height: number;
  base64?: string;
  uri: string;
  exif?: Record<string, unknown> | null;  // ← 追加
};
```

**ポイント解説:**
- `Record<string, unknown>`: キーが文字列、値が何でもよいオブジェクト型。iOSとAndroidでEXIFのキー名が異なるため、厳密な型定義が難しく、この形にしている

---

### `CameraScreen.tsx` — exif: true を追加し画面間で渡す

```typescript
// 撮影時に EXIF を取得するよう指示
const photo = await cameraRef.current.takePictureAsync({
  quality: 1,
  base64: true,
  exif: true,  // ← 追加
});

// 次画面に渡す CapturedPhoto に exif を含める
const captured: CapturedPhoto = {
  uri: preview.uri,
  width: preview.width,
  height: preview.height,
  base64: preview.base64,
  exif: preview.exif as Record<string, unknown> | null | undefined,  // ← 追加
};
```

**ポイント解説:**
- `exif: true` を渡さないと、撮影されても EXIF は返ってこない（デフォルト false）
- `as Record<string, unknown>` は型アサーション（TypeScriptに「この型として扱って」と伝える）。expo-camera の `exif` は `any` 型なので変換が必要

### `aiEditRecipe.ts` — AiEditRecipe に metadata フィールド追加

```typescript
// 既存の型（以前から定義されていた）
export type AiCapturedMetadata = {
  iso?: number | null;
  exposureTime?: number | null;
  whiteBalance?: WhiteBalanceMode | null;
  flashFired?: boolean | null;
};

// AiEditRecipe に metadata を追加
export type AiEditRecipe = {
  // ...既存フィールド...
  metadata: AiCapturedMetadata | null;  // ← 追加
};

export const DEFAULT_AI_EDIT_RECIPE: Readonly<AiEditRecipe> = {
  // ...既存デフォルト値...
  metadata: null,  // ← 追加
};
```

**ポイント解説:**
- `AiCapturedMetadata` 型はすでに定義されていたが `AiEditRecipe` に接続されていなかった。今回でつながった
- `| null` にすることで「EXIFが取れなかった場合」を型で表現できる

---

### `ImageProcessingScreen.tsx` — exif を AiCapturedMetadata に変換して recipe にセット

```typescript
const exif = photo.exif ?? null;
const metadata: AiCapturedMetadata | null = exif
  ? {
      iso:
        typeof exif['ISOSpeedRatings'] === 'number'
          ? exif['ISOSpeedRatings']
          : Array.isArray(exif['ISOSpeedRatings'])
            ? (exif['ISOSpeedRatings'] as number[])[0] ?? null
            : null,
      exposureTime:
        typeof exif['ExposureTime'] === 'number' ? exif['ExposureTime'] : null,
      whiteBalance:
        exif['WhiteBalance'] === 0 ? 'auto' : exif['WhiteBalance'] === 1 ? 'custom' : null,
      flashFired:
        typeof exif['Flash'] === 'number' ? (exif['Flash'] & 0x1) === 1 : null,
    }
  : null;

const recipe: AiEditRecipe = {
  ...DEFAULT_AI_EDIT_RECIPE,
  // ...既存フィールド...
  metadata,  // ← 追加
};
```

**ポイント解説:**
- `photo.exif ?? null`: exif が `undefined` の場合に `null` に統一する（`??` は null/undefined のときだけ右辺を使う）
- `ISOSpeedRatings` は数値のこともあれば配列のこともある（機種差）。両方に対応している
- `exif['Flash'] & 0x1`: ビット演算。Flash の値はビットマスクで、最下位ビット（0x1）が1なら発光済み
- `exif` が `null` の場合（dev デフォルト画像など）は `metadata: null` になる

---

## なぜそう書くか（設計の理由）

- **EXIF を recipe.json に含める理由**: EXIF は `source.jpg` の中にも埋め込まれているが、学習スクリプトが画像から都度読み取るよりも、JSONに整形済みで入っているほうが扱いやすい

- **EXIFを深層学習に使うかは後で決める**: 今は「保存しておく」だけ。フェーズ2（学習設計）で「画像のみ入力」か「画像+メタデータ入力」かを選べるようにするための布石

- **`flashFired` を保存する理由**: FlashFilmはフラッシュ常時ONのアプリだが、まれにフラッシュが発光しないケースがある。そのサンプルを学習から除外するための監査フラグとして使える
